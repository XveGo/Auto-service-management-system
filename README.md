# Тема Курсовой работы: Веб-сервис онлайн-записи и автоматизации учета услуг автосервиса (СТО)

## 1. Описание предметной области
Система предназначена для комплексной автоматизации процессов независимого сервисного центра (СТО). Сервис решает задачи клиентского самообслуживания (онлайн-выбор свободных постов, запись на ТО/диагностику, отслеживание готовности автомобиля), а также внутреннего операционного учета (управление загрузкой ремонтных боксов, назначение мастеров, формирование электронных заказ-нарядов, списание расходных материалов со склада и расчет итоговой стоимости услуг с учетом гарантийной политики).

## 3. Спецификация функциональных требований (FR)

### Модуль А: Клиентский портал и бронирование слотов (Client Booking Module)
* **FR-01 (Каталог услуг):** Система должна отображать актуальный прейскурант работ с группировкой по узлам автомобиля (ДВС, тормозная система, подвеска, ТО) и ориентировочным временем выполнения (нормо-часы).
* **FR-02 (Слот-менеджер):** Система должна рассчитывать доступные временные окна для записи с учетом занятости конкретных подъемников/постов и рабочего графика мастеров.
* **FR-03 (Валидация бронирования):** Система должна требовать при оформлении заявки указание марки, модели авто, госномера и контактного телефона с проверкой маски ввода.
* **FR-04 (Трекинг статуса):** Система должна предоставлять клиенту онлайн-карточку заказ-наряда с отображением текущей стадии («Ожидает заезда», «Диагностика», «В работе», «Готов к выдаче»).

### Модуль Б: Управление производственным процессом и заказ-нарядами (Service Operations Module)
* **FR-05 (Жизненный цикл заказ-наряда):** Система должна переводить заказ-наряд по строгому конечному автомату (Draft -> In_Progress -> Pending_Parts -> Completed -> Closed) с запретом закрытия без фиксации итоговой оплаты.
* **FR-06 (Предотвращение коллизий постов — Race Conditions):** Система должна блокировать одновременное резервирование одного рабочего бокса/подъемника на пересекающиеся временные интервалы при параллельных запросах.
* **FR-07 (Назначение исполнителей):** Система должна позволять прикреплять к одной заявке нескольких механиков с фиксацией персональной выработки (нормо-часов).

### Модуль В: Складской учет и финансовые расчеты (Warehouse & Billing Module)
* **FR-08 (Резервирование и списание ТМЦ):** Система должна проверять фактический остаток запчастей и технических жидкостей на складе и выполнять автоматическое списание в момент включения детали в заказ-наряд.
* **FR-09 (Калькуляция стоимости работ):** Система должна вычислять итоговую стоимость услуги по формуле: `Сумма = (Количество нормо-часов * Ставка) + Стоимость запчастей - Персональная скидка`.
* **FR-10 (Экспорт документации):** Система должна генерировать печатные формы акта приема-передачи автомобиля и заказ-наряда в формате PDF с расчетом НДС и реквизитами сервиса.
* **FR-11 (Журналирование операций):** Система должна сохранять неизменяемую запись в журнал событий при любом изменении перечня работ или ручной корректировке стоимости мастером.

## 4. Нефункциональные требования (NFR) на базе ISO 25010

| Категория ISO 25010 | Контекст предметной области | Инженерная формулировка требования (NFR) |
| :--- | :--- | :--- |
| **Performance Efficiency** | Пиковая нагрузка в сезон смены резины и утренние часы записи. | **NFR-01:** Время отклика API (p95 Latency) при чтении каталога и доступных слотов не должно превышать **200 мс** при нагрузке до **100 RPS**. |
| **Performance Efficiency** | Создание заказ-наряда мастером на приемке. | **NFR-02:** Время проведения транзакции создания заказ-наряда и резервирования бокса в БД не должно превышать **500 мс**. |
| **Reliability** | Бесперебойная работа терминала мастера-приемщика. | **NFR-03:** Коэффициент доступности сервиса (Uptime/Availability) должен составлять не менее **99.5%** в рабочие часы СТО (с 08:00 до 21:00). |
| **Usability** | Использование веб-интерфейса механиками на планшетах в цеху. | **NFR-04:** Пользовательский интерфейс мастера/механика должен быть полностью адаптирован под сенсорные экраны с минимальной диагональю от **9.7 дюймов** (touch-friendly элементы). |
| **Usability** | Быстрая загрузка клиентского интерфейса через мобильный интернет. | **NFR-05:** Начальный размер статического бандла клиентской части не должен превышать **350 Кб** в сжатом виде (brotli/gzip). |
| **Security** | Защита персональных данных автовладельцев (ФИО, телефоны, госномера). | **NFR-06:** Аутентификация сотрудников должна осуществляться по стандарту JWT (с временем жизни access token не более **15 минут** и безопасным хранением в HttpOnly cookie). |
| **Security** | Предотвращение парсинга базы и спам-записей. | **NFR-07:** Для публичных эндпоинтов бронирования должен быть включен Rate Limiting (не более **5 запросов на бронирование в минуту** с одного IP/клиентской сессии). |
| **Maintainability** | Интеграция с внешними каталогами запчастей и номенклатур. | **NFR-08:** Модуль работы со складом должен быть изолирован сервисным слоем (паттерн Repository / Data Mapper) с покрытием бизнес-логики модульными тестами не менее **70%**. |
| **Portability** | Развертывание сервиса на любом локальном или облачном сервере. | **NFR-09:** Все компоненты приложения (бэкенд, фронтенд, база данных) должны поставляться в виде multi-stage `Docker`-контейнеров с запуском через `docker-compose`. |
| **Compatibility** | Корректное отображение на клиентских устройствах. | **NFR-10:** Веб-приложение должно гарантированно поддерживать актуальные версии современных браузеров (Chrome, Safari, Firefox, Edge) за последние **2 года**. |

## 5. Системные ограничения и допущения (Constraints)

* **Constraint-01 (Монолокационность):** Система версии v1.0 рассчитывается на работу **одного физического сервисного центра (одна точка)**. Мультифилиальность и маршрутизация между разными филиалами в первой версии не поддерживаются.
* **Constraint-02 (Временная зона):** Все временные метки событий, записей и графиков работы мастеров фиксируются в едином часовом поясе **(UTC+3, Москва)** без динамического пересчета time zones.
* **Constraint-03 (Платежный контур):** В версии v1.0 исключена прямая интеграция с онлайн-эквайрингом банков; оплата фиксируется вручную отметкой кассира/приемщика («Наличные», «Безналичный расчет через терминал»).
* **Constraint-04 (Типы обслуживаемого транспорта):** Система поддерживает учет только легкового и малотоннажного коммерческого транспорта (категории M1, N1). Учет спецтехники и грузового транспорта с индивидуальной сеткой нормо-часов исключен.
* **Constraint-05 (Формат хранения файлов):** Все прикрепляемые к заказ-наряду диагностические фотографии и акты хранятся во внешнем объектном S3-хранилище (или локальной директории медиафайлов), а в реляционной БД сохраняются только строковые URI (до **255 символов**).
* **Constraint-06 (Ограничение параллельных постов):** Конфигурация СТО программно ограничена максимум **20 параллельно функционирующими постами/подъемниками**.
